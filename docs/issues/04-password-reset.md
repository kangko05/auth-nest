# 비밀번호 재설정

## 문제 상황

비밀번호를 잊은 사용자가 스스로 복구할 수 있는 수단이 없으면 고객 지원에 의존하게 되고, 그 과정에서 사용자가 이탈한다. 운영 비용도 증가한다.

단순히 새 비밀번호를 입력받아 바꿔주는 방식은 이메일 주소를 아는 누구나 타인 계정의 비밀번호를 바꿀 수 있어 보안 문제가 있다. "해당 이메일에 접근할 수 있는 사람"임을 검증하는 수단이 필요하다.

---

## 왜 토큰 방식인가

비밀번호 재설정 시점에는 비밀번호를 모르는 상태이므로 기존 인증 수단을 사용할 수 없다. 이메일로 토큰을 발송하면 이메일 수신 가능 여부 자체가 신원 검증 수단이 된다.

**검토한 다른 방법들**

- 보안 질문 — 예측 가능성이 높고 소셜 엔지니어링에 취약. 현재는 안티패턴으로 분류됨
- OTP (숫자 코드) — 토큰 URL과 보안 수준은 유사하나 코드 입력 UX가 다름. 기능상 차이는 없어 URL 방식 선택

---

## 설계 결정

### 토큰 생성

```typescript
const token = randomBytes(32).toString('hex'); // 64자 hex
```

`crypto.randomBytes`로 예측 불가능한 토큰 생성. UUID 대신 사용한 이유는 UUID가 구조적으로 예측 가능성이 있어 보안 토큰 용도로 적합하지 않기 때문.

### Redis 저장 구조

```
password-reset:{token} → email (TTL: 15분)
```

DB가 아닌 Redis에 저장한 이유:
- TTL로 자동 만료 처리 → 별도 정리 로직 불필요
- 재설정 토큰은 단기 임시 데이터라 DB에 남길 필요 없음

TTL 15분: 너무 길면 탈취된 토큰의 악용 가능 시간이 늘어나고, 너무 짧으면 사용자가 이메일 확인 전 만료될 수 있어 균형점으로 선택.

### 계정 열거 공격 방어

```typescript
async resetPassword(email: string) {
  const foundUser = await this.userService.findByEmail(email);
  if (!foundUser) return; // 이메일 존재 여부와 무관하게 동일 응답
  ...
}
```

이메일이 존재하지 않아도 동일한 응답을 반환해 이메일 존재 여부를 외부에 노출하지 않는다.

### 토큰 즉시 삭제

```typescript
await this.accountService.deleteResetPasswordToken(token);
```

비밀번호 변경 성공 후 토큰을 즉시 삭제해 재사용을 방지한다.

---

## 결과

이메일 수신 가능 여부로 신원을 검증하고, 토큰 TTL과 즉시 삭제로 탈취 및 재사용 위험을 최소화했다.
